Real-time systems rarely fail because a single task is slow; they fail because who preempts whom, when, and how much residual work remains violates architectural assumptions. PTPN (Priority Timed Petri Nets) maps task graphs into places and transitions, captures the OS scheduler as a pluggable Firing Rule, and closes the architecture verification loop for LLM code generation via Timing Skills and counterexample-driven repair.

PART 01 - THE PTPN MODEL & PHYSICAL ENTITY MAPPING Reference Policy: Fixed-Priority Scheduling

What is the PTPN model, and how does it map to physical entities?

Because our Firing Rule corresponds directly to the operating system's scheduling algorithm, we illustrate the model using Fixed-Priority Scheduling, the most widely studied real-time policy. In PTPN, nothing about the schedule is hidden in an external side table: task states are tokens in places, execution intervals are timed transitions, CPU cores and priorities are transition attributes, and preemption is governed by the firing rule.

WCRT(F) = 19 ms = 6 ms (A executes) + 1 ms (F runs during the A->B delay) + 3 ms (B arrives and preempts Core 0 while F freezes at h = 1) + 9 ms (F resumes from h = 1 to complete its 10 ms worst-case work).

Without interval execution times [l, u] and a firing rule that freezes progress at h = 1 upon preemption, an analyzer cannot derive 19 ms. Below is how PTPN models every element.

PHYSICAL ENTITY <-> FORMAL PTPN ELEMENT

How Physical Entities Map to the Net

Hover or click any card below to isolate its places, transitions, and arcs on the canvas:

01. Software Task entry -> get_core -> ready -> exec -> exit

A task is an alternating place/transition path

Each task expands into entry (released) -> get_core (0-time dispatch) -> ready (on core) -> exec (timed CPU segment) -> exit (completed). A task holding k locks expands into 2k + 1 segments.

02. Periodic Timer A_period <-> A_fire [20, 20]

Hardware timer interrupt = self-loop place + release transition

Periodic task A has a timer place A_period initialized with 1 token. Transition A_fire [20,20] (core = -1) fires every 20 ms, depositing a job token in Aentry and returning the timer token to A_period.

03. Task Precedence & IPC Delay Aexit -> A_to_B [1, 1] -> Bentry

Inter-task communication = timed bridge transition

When A finishes, a 1 ms communication delay before B becomes ready is modeled by bridge transition A_to_B [1,1] (core = -1). Because Core 0 is idle during this 1 ms bridge, low-priority F is able to acquire Core 0 and run for 1 ms.

04. CPU Core & Priority @core = 0, @priority = 98 / 97 / 96

Processor core and priority = transition scheduling attributes

Under resume semantics, there is no shared "core place" token to steal. Every CPU transition carries core = 0 and priority = pi; the firing rule ensures at most one transition per core enters Epri.

05. Execution Time & Preemption Context Fexec [2, 10] + suspendable + clock h(t)

Execution interval and saved context = timed transition + clock h(t)

When Fexec is preempted by B, its token stays in Fready and its accumulated execution clock h(Fexec) = 1 freezes (dh/dt = 0), modeling OS context save and resume without losing completed work.

PART 01B - FIRING RULE & STATE-CLASS TRANSITION ANIMATION Driven by Live Analyzer SCG Output

What is the firing rule? How do token flow, preemption freeze, and state transitions interact?

In a standard Petri net, any transition with enough input tokens may fire. In PTPN, the Firing Rule is the scheduling algorithm: at every state class Sk, the net evaluates three sets: structurally enabled transitions Estruct, scheduler-selected active transitions Epri, and preempted transitions R whose execution clocks freeze.

STEP 1 - STRUCTURAL ENABLING E_struct(M) = { t in T | for all p, M(p) >= Pre(p,t) }

Which transitions have enough input tokens?

Every transition whose input places hold the required tokens enters E_struct. This means the action is logically ready, not that it owns the CPU core.

STEP 2 - PRIORITY FILTER (THE SCHEDULER) E_pri(M) = { t in E_struct | pi(t) = max_{core(t')=core(t)} pi(t') }

How does the fixed-priority rule select who runs?

On each CPU core (core >= 0), only the highest-priority enabled transition enters E_pri; non-CPU transitions (core = -1) pass through unfiltered. Only clocks in E_pri advance at rate 1.

STEP 3 - SUSPENSION & STATE TRANSITION R(M) = (E_struct \ E_pri) intersect T_susp, dh/dt = 0

What happens to preempted tasks and state classes?

An in-progress suspendable transition filtered out of E_pri enters R(M): its token stays in place and its clock freezes (dh/dt = 0). When a transition in E_pri reaches [l, u] and fires, tokens move to form the next state class S_{k+1}.

PART 02 - ONE MODEL, MANY SCHEDULING ALGORITHMS Same Net Topology | Pluggable Firing Rule

Adapt to any scheduling algorithm by changing the firing rule. The model itself stays invariant.

Traditional formal models hard-code the scheduler into the net topology, requiring a new net whenever the policy changes. In PTPN, the places, transitions, and arcs describe only the task structure and stay completely unchanged; switching from Fixed Priority to RM, DM, EDF, or FIFO only swaps the firing rule operator that filters Estruct -> Epri.

PART 03 - LLM ARCHITECTURE VERIFICATION, TIMING SKILLS & REPAIR LOOP PTPN / JSON / RTSL + Timing Skill + Witness Feedback

Make LLMs verify whether a task schedule is feasible at architecture design time.

Because modern LLMs generate system and application code directly, discovering a deadline miss or deadlock after implementation forces expensive rewrites. We provide three model forms (RTSL, TDG JSON, and native PTPN) for LLM generation, a Timing Skill to confirm the only parameter an LLM cannot invent-task execution time-and a closed-loop verifier that reports formal counterexamples back to the LLM until all requirements are met.

Three Interchangeable Front Doors: RTSL, TDG JSON, and Native PTPN

      3.3 - Counterexample-Driven Architecture Revision
      
Test with PTPN -> Report Unfeasible Requirements to LLM -> Revise Until Satisfied

      

        Once a PTPN model (in RTSL, JSON, or native PTPN form) has task timings, our analyzer explores
        its state space. If an unfeasible requirement is found (such as a deadline miss or deadlock),
        the analyzer reports the exact diagnostic code and counterexample witness trajectory back to the
        LLM to revise the architecture until all user requirements are satisfied.
