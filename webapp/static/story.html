Priority Timed Petri Nets

A schedule is a sequence of firings.

Real-time systems do not fail because a task is slow. They fail because the timing of who runs, when, and for how long is not what the design assumed. PTPN makes that timing explicit: a task graph becomes a timed Petri net, and every scheduling decision becomes a firing rule.

01 · The problem

WCET is not a schedule.

A task graph tells us what can run. A real-time schedule is a statement about what does run on the shared core — including the time a task spends waiting, and the progress it loses when it is preempted.

WCRT(F) = 19 = 6 (A) + 1 (dependency) + 3 (B) + 9 (F's residual work after preemption). F's WCET is 10: 1 unit before the preemption, 9 after it.

The 19 is not a guess. It is the longest path through the symbolically explored state space, under the fixed-priority firing rule.

A

Intervals, not points

A executes in [4, 6]. Every value in the interval is a legal run. A point WCET hides the schedule's timing envelope.

B

Preemption has a residual

When B arrives, F has already run for 1 unit. F must resume from 1, not from 0. That breakpoint is part of the state.

C

The rule is the scheduler

"Highest priority on the core" is not an annotation. It is an operational rule that decides which transition may fire next.

02 · The model

Tasks become tokens. Timing becomes intervals.

PTPN lowers the task graph into a place/transition net. The structure records what can happen; the annotations record when it may happen. Nothing about the schedule is hidden in a side table.

1 · Task chain

A task is an alternating place/transition path.

entry → get_core → ready → exec → exit. The token is the current state of the task. A timed transition is an execution segment, not a label on the whole task.

2 · Periodic release

A clock can create a token.

A_period → A_fire [20,20] → Aentry. The release transition carries time; it is not a CPU-scheduled step.

3 · Dependency

An edge becomes a bridge transition.

Aexit → A_to_B [1,1] → Bentry. The delay is explicit. A fork/join would wire directly into a sync transition instead.

4 · Core and priority

The core is a scheduling attribute.

Under the resume policy there is no core token to steal. A transition carries core = 0 and priority = 97; the firing rule keeps at most one task per core.

5 · Time

Only execution and release transitions consume time.

Acquire, lock, fork/join and connector transitions are zero-time. This is why the net can represent a schedule without inventing a global clock tick.

03 · The firing rule

The scheduler is a filter over enabled transitions.

At every state, the net computes three sets. A task can be structurally ready and still not run. The difference between the first two sets is exactly the scheduling decision.

04 · One model, many rules

Change the firing rule, not the task graph.

The net records the possible behaviours. A scheduling policy is an operational answer to one question: given the enabled transitions, who may run on this core? The same source model can be analysed under different rules.

Supported classes

A rule is not a magic switch

EDF and FIFO in this analyzer are restricted to statically partitioned systems with one in-flight job per task, no locks, no fork/join and no dependency-driven releases. The hw example has a dependency, so those rules are rejected with E-UNS-001 rather than silently approximated. Structural restart is a lowering variant, not a pure firing-rule swap: it adds preemption transitions to the net.

05 · The LLM loop

Let the model be generated. Let the analyzer be the judge.

An LLM can draft the architecture, but it cannot certify its own timing. PTPN gives the model three interchangeable front doors, a disciplined timing hand-off, and a verdict that can be fed back into the next revision.
